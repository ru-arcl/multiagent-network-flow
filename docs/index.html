Optimal Multirobot Path Planning on Graphs: Complete Algorithms and Effective Heuristics

Jingjin Yu and Steven M. LaValle

Labeled robots share a graph and must all reach their own goals without meeting at a vertex or swapping along an edge; we turn this into an integer flow on a time-expanded network, solve it exactly as an integer linear program, and split big instances over time to get near-optimal plans fast.

How it works

1. Time expansion

Fix a horizon T. Copy every vertex v of the graph 2T + 1 times: v(0), v(1), v(1)′, …, v(T), v(T)′. Green arcs v(t)′ → v(t+1) let a robot wait; blue arcs v(t) → v(t)′ have capacity 1, so no two robots meet at a vertex. Every collision-free plan with at most T steps gives an integer multiflow of value n, and every such flow gives a plan (Theorem 1). Several flows can give the same plan, so the map is onto but not one-to-one (erratum E4).

2. The merge-split gadget

Each edge {u, v} and step t gets the gadget of Fig. 4(b): both directions share one middle arc of capacity 1, so two robots cannot swap along an edge (a head-on collision). The compact model (Figs. 6, 7) keeps two binary variables per robot, edge and time step (one per direction), plus one per robot, vertex and step for waiting, and drops arcs no robot can reach.

3. Integer linear programs

Every robot gets its own binary flow variables. For the makespan, maximize the flow on the loopback arcs and raise T from the shortest-path lower bound until all n robots arrive (Algorithm 1). Total arrival time, total distance and max distance use the same network with different costs and a horizon search, so all four algorithms are complete and optimal.

4. The k-way split

Exact models grow quickly with T. The heuristic cuts every robot's shortest path in the middle, uses the midpoints (moved to free vertices when they clash) as intermediate goals, and solves the 2 halves; repeating gives 4, 8 or 16 pieces, glued end to end. The pieces are often smaller models than the exact one, but not always: on a crowded graph a piece can need as many steps as the whole plan (the 9-puzzle's 4-way split has pieces of 3, 5, 4 and 4 steps against an optimal makespan of 4), and its model is then larger. Open the split example of Fig. 8 with k = 2 to see the cost: makespan 5 instead of 4.

About this demo

The plans marked precomputed were computed by docs/data/build_demo_data.py with the Python package mppflow, a port of our original Java code, using Gurobi (or HiGHS when Gurobi is unavailable); each plan records its solver. Live solves run docs/js/engine.js and docs/js/lp.js, a line-by-line JavaScript port of the package's builtin simplex and branch-and-bound solver, in a Web Worker. Parity tests require the JavaScript results to equal the Python ones exactly, so a live solve that finishes within its time limit repeats the builtin Python run pivot for pivot (with the same seed); where a binding time limit stops a solve depends on the machine. The live time limit covers the whole solve, while mppflow.plan(split=k) gives each piece the full limit. Everything runs locally; the page loads nothing from the network.
